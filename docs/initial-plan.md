# 메니에르 환자를 위한 증상 기록과 생활 관리 앱 기획서

**증상 기록과 진료 준비, 생활 습관 관리를 함께 돕는 앱을 기획한다.** 사용자는 2026-10-03 이 두 영역을 우선 해결할 문제로 선택했다. 증상을 짧게 남기고 일상에서 챙길 습관을 관리하며, 진료 전에 필요한 내용을 한 장으로 정리한다. 몸이 좋지 않을 때는 입력을 미룰 수 있어야 하고, 기록하지 않은 날을 증상이 없었던 날로 계산하지 않아야 한다. 환자가 자신의 경험을 의료진에게 설명하는 일을 돕는 것이 첫 제품의 목표다.

이 문서는 제품 검토용 초안이다. 환자 인터뷰와 의료진 검토는 아직 하지 않았다. 두 핵심 문제 외의 구체 기능, 타깃, 가격, 일정, 검증 목표는 승인 전 제안이며 임상 효과나 시장 수요가 검증됐다는 뜻이 아니다.

## 1 한 줄 요약

메니에르 환자가 **발작과 귀 증상을 기록하고, 자신에게 필요한 생활 습관을 관리하며, 진료에 가져갈 요약을 만드는 앱**이다.

아플 때 짧게 남기고 회복 후 보완하며, 평소에는 부담 없이 생활 습관을 점검한다. 진료 요약에서는 의료진이 기록의 빈칸까지 알아볼 수 있게 한다. 사용 시간이 길어지는 것보다 필요한 기록을 적은 부담으로 마치는 것을 성공으로 본다.

## 2 문제와 근거

### 의료 자료에서 확인한 사실

메니에르병은 회전성 어지럼, 이명, 청력 저하, 귀가 꽉 찬 느낌 등을 동반할 수 있다. 증상의 간격과 양상은 사람마다 다르며, 진단은 병력과 청력검사 등을 포함한 의료진의 평가가 필요하다. 따라서 앱의 증상 선택이나 지속 시간만으로 메니에르병 여부를 판정하지 않는다. [NIDCD 질환 설명](https://www.nidcd.nih.gov/health/menieres-disease)

식이·생활 습관 조절이 권고되는 경우가 있지만, 2023년 Cochrane 검토는 해당 중재의 효과 근거가 매우 불확실하다고 평가했다. 이 검토의 검색 시점은 2022년 9월이며 최신 연구를 모두 반영한다는 뜻은 아니다. 앱은 커피, 수면, 식사 기록을 개인의 원인이나 치료법으로 단정하지 않는다. [Cochrane 검토](https://www.cochrane.org/evidence/CD015244_what-are-benefits-and-risks-different-lifestyle-and-dietary-changes-menieres-disease)

### 인터뷰로 확인할 문제 가설

| 가설                                            | 제품에 반영할 제안                               | 확인 방법                       |
| ----------------------------------------------- | ------------------------------------------------ | ------------------------------- |
| 증상이 심하면 휴대폰을 보기 어렵다              | 나중에 기록하기를 시작 버튼과 같은 비중으로 배치 | 최근 발작 때 실제 행동 인터뷰   |
| 진료 때 시작 시각과 지속 시간을 기억하기 어렵다 | 대략적인 시각과 시간 미상을 허용                 | 기존 메모와 진료 준비 과정 관찰 |
| 발작 횟수만으로 생활의 어려움이 전달되지 않는다 | 회복까지 걸린 시간과 일상 중단 정도를 따로 기록  | 환자와 의료진 각각 검토         |
| 매일 자세히 입력하면 오래 사용하기 어렵다       | 필수 입력 최소화, 생활 기록은 선택               | 2주 사용성 평가                 |
| 빈칸이 정상인 날로 해석될 수 있다               | 무증상 확인과 미기록을 별도 표시                 | 요약 해석 과제                  |

### 기존 대안과 차별화 가설

2026-10-03 공식 웹 소개를 확인했다. 설치·결제·실사용 검증은 하지 않았으므로 아래는 사업자의 설명 기준이다.

| 대안                                                       | 확인된 내용                                                                 | 우리 기획에 주는 의미                             |
| ---------------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------- |
| [Menierly](https://www.menierly.com/)                      | 증상·발작 기록, 로컬 저장, CSV 내보내기, 일회성 결제로 PDF와 장기 이력 제공 | 기록과 PDF 자체는 차별점이 아니다                 |
| [Menieres Biometrics](https://www.menieresbiometrics.com/) | Android에서 청력 관련 측정, 증상 일지, 변화 시각화, CSV 제공을 소개         | 첫 버전에 청력 측정까지 넣기보다 기록 품질에 집중 |
| 종이·기본 메모 앱                                          | 비교 대상 후보, 환자의 실제 사용 방식은 미조사                              | 추가 앱을 설치할 만큼 편한지 직접 비교 필요       |

경쟁 앱에 특정 기능이 없다고 확인한 것은 아니다. **회복 후 기록의 편의, 기록 누락을 드러내는 요약, 진료에서의 읽기 쉬움**을 차별화 가설로 검증한다. 경쟁 앱보다 낫다는 표현은 비교 사용성 평가 이후에만 쓴다.

첫 버전에서 발작 예측, 자동 진단, 치료 추천, 청력 자가검사, AI 의료 상담, 커뮤니티, 실시간 보호자 추적은 제외하는 안을 제안한다. 이들은 기록 도구와 다른 정확성·운영 책임을 요구한다.

## 3 사용자와 사용 상황

1차 타깃 제안은 의료진에게 메니에르병 진단을 받고 외래 진료를 이어가는 성인이다. 글로벌 사용을 기본으로 영어·한국어 문구를 준비하되 첫 출시 국가와 모집 언어는 확정 필요다. 미진단 사용자를 진단 도구로 유입시키지 않는다.

| 상황                              | 사용자가 원하는 결과             | 제안하는 행동                         |
| --------------------------------- | -------------------------------- | ------------------------------------- |
| 증상이 시작됐고 화면을 볼 수 있음 | 시작 시각만 남기기               | 시작 한 번 누르고 휴대폰 내려놓기     |
| 증상이 심해 앱을 못 씀            | 기록 때문에 부담받지 않기        | 회복 후 대략적인 과거 기록 작성       |
| 평소 저녁                         | 상태와 생활 습관을 짧게 점검하기 | 증상 상태와 선택한 습관 1~3개 확인    |
| 병원 방문 전                      | 기억을 정리하고 질문 준비        | 기간 선택 후 한 장 요약 확인          |
| 가족에게 도움을 요청할 때         | 미리 정한 사람에게 연결          | 전화·문자 앱 열기, 전송은 사용자 실행 |

입력 시간 목표는 짧은 기록 10초 안팎, 하루 확인 30초 이내다. 실측 전 제품 목표이며 실제 발작 중 사용을 강요하거나 시험하지 않는다.

## 7 핵심 사용자 흐름과 화면

**첫 실행:** 용도·기기 저장 안내 → 선택형 기본 설정 → 홈. 이름, 생년월일, 병원명, 진단 증명서는 필수로 받지 않는다. 알림과 연락처 설정도 건너뛸 수 있다.

**기록:** 홈에서 ‘지금 시작’ → 시작 시각 즉시 저장 → 나중에 종료와 상세 보완. ‘나중에 기록’은 별도 동등 버튼이다. 앱을 닫거나 재시작해도 진행 중 기록을 유지하며, 종료를 잊으면 시간 미확정으로 남긴다.

**생활 관리:** 챙길 항목 1~3개 선택 → 원하는 경우 알림 설정 → 하루 확인 → 주간 기록 돌아보기. 미완료를 질병 악화나 의지 부족으로 연결하지 않는다.

**진료 준비:** 기간 선택 → 기록 요약 → 의료진에게 물어볼 질문 작성 → 미리보기 → 파일 저장 또는 시스템 공유. 의료진에게 자동 전송하지 않는다.

| 화면      | 핵심 내용                                           | 예외와 접근성                              |
| --------- | --------------------------------------------------- | ------------------------------------------ |
| 홈        | 지금 시작, 나중에 기록, 오늘 상태와 습관, 진료 준비 | 긴 설문·로그인·광고로 진입을 막지 않음     |
| 짧은 기록 | 시작 시각과 저장 상태                               | 실수한 시작은 취소·수정 가능               |
| 기록 상세 | 증상, 지속 시간, 생활 영향, 회복 시점               | ‘기억 안 남’, ‘대략’ 선택 가능             |
| 기록 목록 | 날짜별 기록과 빈 날                                 | 색만으로 상태를 구분하지 않음              |
| 생활 관리 | 선택한 습관, 하루 확인, 주간 기록                   | 건너뛰기 가능, 달성률로 건강 평가하지 않음 |
| 진료 요약 | 날짜 범위, 기록 수, 미확정 값, 질문                 | 큰 글씨와 표의 텍스트 대체 제공            |
| 도움      | 안전 안내, 미리 정한 연락처                         | 연락 앱 열기와 실제 연락 완료 구분         |
| 설정      | 알림, 내보내기, 백업, 복구, 삭제                    | 삭제 전 대상·복구 가능 여부 확인           |

제안하는 화면 기준은 기본 글씨 18 이상, 주요 터치 영역 48 이상, 확대 글씨에서도 버튼 잘림 없음이다. 회전·맥박 효과, 자동 스크롤, 움직이는 차트와 연속 기록 보상은 사용하지 않는다. 밝고 어두운 테마를 모두 검토하고 소리만으로 정보를 전달하지 않는다.

## 8 저장과 개인정보 설계

초기안은 계정 없이 사용하고 건강 기록은 기기에 보관한다. 최소 수집 원칙으로 위치, 주소록 전체, 마이크, 사진 권한은 요구하지 않는다. 도움 연락처는 직접 입력할 수 있게 한다.

| 서비스                                            | 첫 버전 제안                                          |

| Firebase Auth·Firestore·Realtime Database·Storage | 사용하지 않음 · 동기화 승인 시 재검토                 |
| Cloud Functions·Cloud Run                         | 사용하지 않음 · 유료 기능 서버 검증을 도입하면 재설계 |

저장 파일 암호화와 운영체제 보안 키 저장소를 검토한다. 운영체제 자동 백업에 건강 원본이 포함되는지 명시적으로 제어하고 실제 기기로 검증한다. 앱 전환 미리보기와 잠금 화면 알림에는 증상·약 이름을 노출하지 않는 것을 기본으로 한다.

수동 백업은 암호화된 복구 파일, 진료용 PDF와 CSV는 공유용 파일로 구분한다. 공유 파일에는 민감한 기록이 들어간다는 점을 미리 알리고 시스템 공유 화면에서 수신자를 직접 고르게 한다. 내보낸 파일은 앱 삭제로 회수되지 않는다. 임시 공유 파일은 정해진 수명 후 제거한다.

복원은 건수와 기간 미리보기 후 명시적 선택으로 수행한다. 같은 기록 ID는 중복 생성하지 않고 충돌이 생기면 임의 덮어쓰기를 하지 않는다. 손상·버전 불일치·잘못된 비밀번호는 기존 자료를 보존한 채 실패 처리한다.

증상·복약·자유 메모·의료기관·연락처·내보낸 문서 내용을 분석 도구, 크래시 로그, AI 서비스에 전송하지 않는다. 로컬 기록만 쓰더라도 출시 국가별 개인정보 의무가 면제된다고 가정하지 않는다. 법적 분류와 보존·삭제 정책은 출시 국가가 정해진 후 전문 검토가 필요하다.

## 10 기록 항목과 진료 요약 규칙

### 기록 항목

- 발작: 기록 ID, 발생일, 시작·종료 시각, 정확함·대략·모름, 입력 시각, 시간대, 증상, 일상 영향, 회복 시점, 선택 메모.
- 귀 증상: 이명, 먹먹함, 주관적 청력 변화와 좌·우·양쪽·모름. 주관적 청력 변화는 청력검사 수치와 구분한다.
- 하루 상태: 증상 없음·증상 있음·미기록. ‘증상 없음’은 사용자의 명시적 입력이 있어야 한다.
- 생활 기록: 선택형 수면 시간, 주관적 스트레스, 음식·음료 메모. 정해진 물·나트륨 목표나 생활 점수를 기본 제공하지 않는다.
- 치료 관련 메모: 본인이 입력한 복약·치료 변경 사실만 기록. 용량 변경과 복약 여부를 권고하지 않는다.
- 진료 준비: 방문일, 본인이 물어볼 질문, 선택형 의료진 설명 메모.

### 생활 습관 관리의 구체 범위

생활 관리 기능 자체는 핵심 범위에 포함한다. 다만 모든 항목을 매일 입력하게 하지 않고 사용자가 자신의 상황에 맞게 선택하도록 한다. 습관을 잘 지켰다는 이유로 발작을 예방했다고 표시하지 않는다.

| 선택 항목               | 하루 입력 예시                                | 앱이 제공하는 도움                                |
| ----------------------- | --------------------------------------------- | ------------------------------------------------- |
| 수면                    | 취침·기상 시각 또는 대략적인 수면 시간        | 선택형 취침 준비 알림과 일주일 기록               |
| 스트레스와 휴식         | 오늘 느낀 부담 3단계, 쉬는 시간 가졌음·건너뜀 | 사용자가 정한 휴식 알림, 평가 없는 기록           |
| 식사와 음료             | 평소와 다른 식사, 카페인·음주 여부 또는 메모  | 기록을 진료 질문과 연결, 금지 식품 자동 판정 없음 |
| 의료진과 정한 생활 계획 | 본인이 입력한 계획, 실천함·일부·건너뜀        | 정한 시간에 알림, 필요 시 계획 수정               |

첫 버전에는 식품 데이터베이스, 음식 사진 분석, 자동 나트륨 계산을 넣지 않는 안을 제안한다. 반복 입력과 영양 데이터 관리 비용이 핵심 가치에 비해 큰지 먼저 확인한다. 수분·나트륨의 수치 목표는 앱이 자동 생성하지 않는다.

주간 화면은 ‘수면을 기록한 날 5일, 어지럼을 남긴 날 2일’처럼 사실만 보여준다. 서로 다른 기록의 날짜를 나란히 볼 수 있지만 위험 색상·원인 순위·인과 점수는 만들지 않는다. 사용자가 ‘이 변화에 대해 다음 진료에서 물어보기’를 눌러 질문으로 옮길 수 있다.

알림은 모두 선택형이며 기본 하루 한 번의 묶음 확인을 제안한다. 아픈 날에는 알림을 쉬게 할 수 있고, 기록을 놓쳐도 연속 달성 기록이나 보상을 잃지 않는다. 알림의 실제 전달을 보장하지 않으며 중요한 치료 지시를 알림 하나에 의존하게 하지 않는다.

### 집계 규칙

1. ‘기록된 발작 수’라고 표시한다. 실제 총발작 수나 질병의 중증도 점수로 표현하지 않는다.
2. 명시적으로 하루 상태를 입력한 날짜 수와 전체 기간을 함께 표시한다. 발작만 기록한 날은 하루 전체를 관찰한 것으로 취급하지 않는다.
3. 종료 미정은 지속 시간 평균에서 제외하고 제외 건수를 표시한다. 대략 입력한 시간은 별도로 표시한다.
4. 기간 밖에서 시작하거나 끝나는 발작은 경계를 표시하고 중복 계산하지 않는다. 날짜 귀속은 저장된 발생지 시간대를 기준으로 하며 여행·서머타임을 시험한다.
5. 어지럼이 끝난 시점과 일상 복귀 시점을 분리한다. 시간 미상은 0시간으로 바꾸지 않는다.
6. 생활 기록은 시간순으로 함께 보여줄 수 있지만 ‘원인 발견’, ‘위험도’, ‘내일 발작 확률’을 계산하지 않는다.
7. 이전 기간과 비교할 때 기록한 날짜 수가 다르면 그 차이를 함께 표시한다. 기록 감소를 호전으로 해석하지 않는다.

**가상 요약 예시:** ‘최근 28일 중 하루 상태를 남긴 날 17일. 기록된 발작 3건. 지속 시간을 알 수 있는 기록 2건, 종료 미정 1건. 생활에 큰 지장이 있었다고 남긴 날 2일. 미기록 11일.’ 이 예시는 실제 환자 데이터가 아니다.

첫 페이지에는 위 요약, 발작별 날짜·시간·주요 증상, 일상 영향, 질문 3개를 싣는다. 긴 상세 기록은 다음 페이지에 둔다. 환자가 기록한 자료이며 누락과 기억의 오차가 있을 수 있다는 설명과 생성일을 표시한다.

## 11 의료 문구와 도움 화면

의료 설명은 공개 자료를 근거로 자체 작성하고 출처·검토일을 관리한다. 출시 전 이비인후과 의료진의 문구 검토를 받는다. 검토되지 않은 생성형 답변을 환자에게 제공하지 않는다.

| 허용할 표현                            | 쓰지 않을 표현                        |
| -------------------------------------- | ------------------------------------- |
| 입력한 기록을 진료 전에 정리합니다     | 메니에르병을 진단합니다               |
| 수면과 증상을 함께 살펴볼 수 있습니다  | 수면 부족이 발작의 원인입니다         |
| 의료진과 상의한 내용을 메모하세요      | 나트륨·수분·약 용량을 이렇게 바꾸세요 |
| 기록이 없는 날은 상태를 알 수 없습니다 | 이번 달은 완치에 가까워졌습니다       |

도움 화면의 의료진 검토용 초안은 다음과 같다.

- 어지럽다면 운전을 멈추고 안전한 곳에서 도움을 받도록 안내한다.
- 어지럼과 함께 갑작스러운 얼굴 처짐, 팔의 힘 빠짐, 말하기 어려움, 시야 이상, 심한 균형 이상 등이 있으면 평소 메니에르 증상으로 단정하지 않고 즉시 지역 응급 도움을 받도록 안내한다. [NHS 메니에르 안내](https://www.nhs.uk/conditions/menieres-disease/)
- 갑작스러운 청력 저하는 기록만 남기고 기다리지 말고 신속하게 의료기관의 평가를 받도록 안내한다. [NHS 청력 저하 안내](https://www.nhs.uk/conditions/hearing-loss/)

이 목록으로 응급 여부를 판정하거나 ‘위험하지 않음’을 표시하지 않는다. 응급 연락처는 출시 국가별로 검증하며 언어만으로 국가를 추정하지 않는다. 도움 버튼은 로그인·유료 결제·증상 설문 없이 접근하게 한다. 앱은 구급 요청 접수, 보호자의 응답, 의료진 모니터링을 보장하지 않는다.

FDA는 소프트웨어의 기능과 위험에 따라 규제 접근을 구분한다. 이 기획이 기록 중심이라는 이유나 면책 문구만으로 의료기기 해당 여부를 확정하지 않는다. 출시 국가별 실제 기능·홍보 문구를 기준으로 검토한다. [FDA 소프트웨어 정책](https://www.fda.gov/medical-devices/digital-health-center-excellence/device-software-functions-including-mobile-medical-applications)

## 12 마켓 등록과 수익화 계획

각 마켓의 앱 이름, 카테고리, 건강 정보 관련 선언, 개인정보 표기, 연령 등급, 심사 계정 필요 여부는 구현 범위 확정 후 작성한다. Google Play 내부 테스트, App Store TestFlight, AppsInToss preview를 각각 검증하고 등록·업로드·심사·공개를 구분한다. 현재 등록 또는 제출한 것은 없다.

**수익화 제안:** 검증판은 무료로 운영하고, 이후 선택형 편의 기능을 일회성 결제로 제공하는 안을 먼저 검토한다. 기본 기록 열람, 기본 진료 요약, 원본 내보내기, 도움 화면은 무료 유지안을 제안한다. 장기적으로 운영비가 드는 동기화를 제공할 경우에만 구독의 필요성과 가격을 다시 검토한다.

광고는 첫 버전에서 제외하는 안을 제안한다. 아픈 상황의 사용 흐름을 방해할 수 있고 건강 데이터와 광고 도구를 함께 다뤄야 하는 부담이 있다. 이는 승인 전 제품 판단이다. 경쟁 제품에도 무료 기록과 일회성 결제 방식이 있으므로 유료 수요를 이미 확보했다고 보지 않는다.

시장 규모·매출·유료 전환율은 아직 추정하지 않는다. 환자 수를 곧바로 잠재 구매자 수로 계산하지 않는다. 개발비 외에 의료진 검토, 번역, 개인정보·규제 검토, 접근성 QA, 고객 지원, OS 업데이트 비용을 포함해 사업성을 판단한다.

## 13 출시 이미지 계획

이미지는 승인된 실제 화면을 기반으로 만들고 가상의 기록임을 밝힌 예제만 사용한다. 초기 스토어 장면은 ‘나중에 기록’, ‘나에게 맞는 생활 습관’, ‘진료 전 한 장 요약’ 세 가지를 우선한다. 환자 사진, 치료 전후 표현, 완치 보장 문구는 쓰지 않는다. 아이콘·화면 캡처의 규격은 마켓별 등록 시 최신 요구사항을 확인한다.

## 14 검증 지표

사용 횟수와 체류 시간보다 기록 부담과 진료 준비의 유용성을 본다. 아래 수치는 의사결정을 위한 제안 기준이며 관측 결과가 아니다.

| 질문                       | 측정 방법과 통과 목표 제안                                                              |
| -------------------------- | --------------------------------------------------------------------------------------- |

| 과거 기록을 남길 수 있는가 | 10명 중 8명 이상이 대략적인 시각과 종료 미상을 올바르게 입력                            |

임상 증상 감소는 초기 제품의 성과 지표로 주장하지 않는다. 소규모 사용자 평가는 치료 효과를 입증하지 않는다.

초기 평가는 동의받은 사용성 관찰과 설문으로 진행한다. 운영 분석을 추가한다면 ‘화면 진입’, ‘저장 동작 성공’, ‘문서 생성 성공’ 같은 최소 사건부터 개인정보 검토 후 도입한다. 앱 사용 사실 자체도 건강 관심을 드러낼 수 있으므로 증상 값을 빼는 것만으로 안전하다고 판단하지 않는다. 이벤트 원격 전송과 GA4 연결은 미확정이다.

## 15 사람 테스트 계획

환자 8~12명, 이비인후과 의료진 2~3명을 모집하는 안을 제안한다. 아직 모집하지 않았고 의료진 참여가 확정되지 않았다. 진단 시기, 발작 빈도, 사용 기기, 기록 습관이 서로 다른 사용자를 포함한다. 실제 발작을 유도하거나 증상이 심할 때 앱 사용을 요구하지 않는다.

먼저 최근 진료 준비 경험과 기존 기록물을 자발적으로 설명받는다. 이후 가상 기록으로 시작·종료·나중에 기록·요약 읽기를 시험한다. 실제 건강 기록을 수집하는 평가로 확대할 경우 목적, 최소 항목, 동의, 접근자, 삭제 시점을 별도로 정한다.

큰 글씨, 한 손 조작, 작은 화면, 화면 읽기 기능, 청각 정보 없이 사용하기를 검증한다. 의료진에게는 진단 정확성 평가가 아니라 요약의 이해도와 빠진 정보를 묻는다.

## 16 구현 이후 검증 계획

아직 코드와 실행 가능한 검증 명령은 없다. 승인 후 앱 저장소의 실제 명령에 아래 항목을 연결한다.

- 시간 미상·추정 시간·월 경계·시간대 변경·중복 기록·종료 누락의 집계 시험.
- 오프라인, 강제 종료, 앱 업데이트 후 저장 보존과 진행 중 기록 복구.
- 암호화 백업 복원, 손상 파일, 잘못된 비밀번호, 기존 기록과 충돌 시험.
- PDF와 화면 합계 일치, 긴 한글·영문, 글씨 확대, 다중 페이지 잘림 검사.
- 공유 취소·연락 앱 부재·알림 거부·저장 공간 부족의 실패 안내.
- 네트워크와 로그 점검으로 건강 원문·연락처·자유 메모의 외부 유출 부재 확인.
- 출시 국가별 도움 연락처와 의료 문구 검토, 계정·SDK·정책 선언 대조.

기획 검토와 코드 검증, 실기기 검증, 임상 효과 검증은 서로 다른 상태로 관리한다.

## 17 다음 단계와 승인 조건

1. 핵심 문제·1차 타깃·수익화·콘텐츠 출처·제품명 후보를 사용자와 좁힌다.
2. 환자 인터뷰와 의료진 검토로 지금 제안한 문제가 실제로 중요한지 확인한다.
3. 대표 화면과 진료 요약 시제품으로 입력 부담을 검증한다.
4. 출시 국가, 의료·개인정보 범위, 저장·복구 방식, 마켓 범위와 비용을 확정한다.
5. 기획 승인 후 구현 계획과 개발 일정을 산정한다.

조사·시제품 검증에 3~4주를 배정하는 안을 제안하지만 모집과 의료진 일정에 따라 달라진다. 개발 기간과 출시일은 아직 확정하지 않는다.

승인 전에 해결할 항목은 타깃, 반복 사용 가치, 의료 문구 검토 담당, 데이터 보관·복구 방식, 유료 기능의 가치, 지원 마켓·국가다. 기록 부담이 기존 메모보다 크거나 의료진에게 유용하지 않다면 기능을 줄이거나 기획을 재검토한다.
